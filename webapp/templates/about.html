About this system

How the ransomware detector works under the hood

Overview

This is a behaviour-based ransomware detection system built as a final year project. Rather than relying on signatures of known malware, which other prominent systems use, it watches file system activity and uses machine learning to spot the patterns that ransomware tends to create when encrypting files (rapid renames, .locked extensions, bursts of modifications, and accesses to decoy "honeyfiles").

Detection pipeline

👁️

1. File monitor

A watchdog observer continuously logs every file create, modify, delete and rename event in the watched folder.

📐

2. Feature extraction

For each event, a 5-second sliding window is summarised into 8 features: event counts by type, unique files, rename rate, .locked rate, and honeyfile touches.

🌳

3. ML classifier

A Decision Tree (compared against Random Forest) is trained on labelled normal and ransomware events. The final model achieved 98.61% accuracy in a test run which is more realistic than an outright 100%

🚨

4. Alerting

The model scores every new event in real time. When ransomware-like behaviour is detected, an alert is logged with a cooldown to prevent spam and to avoid being locked out.

🍯 Honeyfiles

Honeyfiles are decoy files placed in the watched folder. Their names are produced to look valuable to ransomware (e.g. _AAA_passwords.txt) but a real user has no reason to touch them, which is why they are used as bait.

Because no legitimate process or person should ever read or modify these files, any access at all is a strong signal of malicious behaviour. The system uses honeyfile activity as one of its eight ML features, and any alert that involves a honeyfile is automatically classified as CRITICAL.

Tech stack

  • Language: Python 3.12
  • File system events: watchdog
  • Data processing: pandas
  • Machine learning: scikit-learn (Decision Tree, Random Forest)
  • Web dashboard: Flask + Jinja2
  • UI / charts: Tailwind CSS, Chart.js

Limitations & future work

  • The system watches a single folder. Real EDR tools watch the entire file system at the OS level.
  • Training data is synthetic and generated by a simulator. A production model would need real-world telemetry.
  • No authentication on the dashboard. A real application would use hashed passwords, sessions, and role-based access for SOC analysts.
  • The monitor runs as a foreground process (no buttons to start the scan). In production it would be packaged as a system service (launchd / systemd) that starts on boot.
  • Alerts only print and log and no automated response. Future versions could back up touched files.
